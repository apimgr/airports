# External Integrations

The Airports server is designed to run with **no required external dependencies** beyond a TCP socket. Every integration below is optional and gracefully degrades if unavailable.

## GeoIP — ip-location-db

| Item | Value |
|------|-------|
| Provider | [ip-location-db](https://github.com/sapics/ip-location-db) (GitHub Release assets) |
| Files | `iptoasn-asn.mmdb`, `iptoasn-country.mmdb`, `dbip-city-ipv4.mmdb`, `dbip-city-ipv6.mmdb` |
| License | PDDL (ASN and country); CC BY 4.0 (city) |
| Format | MaxMind MMDB binary |
| Update cadence | Weekly, Sunday at 03:00 local time |
| Storage | `{data_dir}/security/geoip/` |
| Required? | No — server runs without GeoIP; home page falls back to a generic view |

All four databases download from GitHub Releases and are checked against their
published SHA-256 checksum assets before installation. The DB-IP city databases
download from the project's GitHub Releases.

Used for:

- Caller location detection on the home page (to surface nearby airports).
- ASN attribution in abuse-investigation logs.

GeoIP lookup results for callers are **never logged or stored** — they are computed per-request and discarded.

### Disabling GeoIP

```yaml
# server.yml
server:
  geoip:
    enabled: false
```

When disabled, the home page shows a generic view without caller-location results. The scheduler uses `server.scheduler.tasks.geoip_update.schedule` for refresh timing; its default is `0 3 * * 0`.

## Airport Dataset — embedded

The 35,000+ airport records are baked into the binary at compile time from the [OurAirports](https://ourairports.com/data/) public dataset. There is **no runtime fetch** of airport data. Updating the dataset requires rebuilding the binary and shipping a new release.

## TLS Certificates — Let's Encrypt (optional)

| Item | Value |
|------|-------|
| Provider | Let's Encrypt via ACME v2 |
| Challenge types | HTTP-01 (default), DNS-01 |
| Endpoint | `https://acme-v02.api.letsencrypt.org/directory` |
| Storage | `{config_dir}/ssl/acme/` |
| Renewal | Automatic (every 12 hr check, renew at < 30 days remaining) |
| Required? | No — operator may supply their own cert/key, or use HTTP-only |

Enable in `server.yml`:

```yaml
tls:
  enabled: true
  acme:
    enabled: true
    email: ops@example.com
    domains: [airports.example.com]
    challenge: http-01
```

## Tor — Hidden Service (required, auto-detected)

The binary owns Tor entirely — it generates `torrc`, manages hidden-service keys, and starts/stops the Tor process. The onion service points to a dedicated `127.0.0.1` backend listener, separate from clearnet HTTP. Tor sends each request's circuit token in a required HAProxy PROXY-protocol header; the server uses this trusted metadata to identify Tor traffic and count `tor_requests_total`. A `.onion` Host header alone never establishes Tor identity.

| Item | Value |
|------|-------|
| Binary | `tor` (Alpine package; bundled in Docker image) |
| Config | `{config_dir}/tor/torrc` (generated by server binary) |
| Keys | `{data_dir}/tor/site/hs_ed25519_*` (perms 0600) |
| Hostname | `{data_dir}/tor/site/hostname` (the `.onion` address) |
| Backend | Dedicated loopback listener with required PROXY v1 circuit-ID metadata |
| Enablement | Starts whenever the `tor` binary is found; there is no enable/disable setting |

If Tor fails to start the server continues without it; the warning is logged.

## I2P — Eepsite (optional)

I2P is opt-in on bare metal and in a VM, and enabled by default in a
container. The server manages the eepsite lifecycle through its configured
provider and exposes its status through `/server/healthz`. The I2P address is
available on the help page while the eepsite is enabled and running. I2P
requests use HTTP over the overlay and do not receive TLS redirects or HSTS.

Configuration is available through `server.i2p` in `server.yml`, the
`I2P_ENABLED` environment variable, and the `--i2p` CLI option. The server
uses `{config_dir}/i2p/` for generated provider configuration and
`{data_dir}/i2p/` for runtime data and destination keys.

## Model Context Protocol (MCP)

The server exposes remote Streamable HTTP MCP at
`/api/{api_version}/server/mcp`, with aliases `/api/mcp` and `/mcp`. MCP
requests reuse API Bearer authentication and require a linked owner token
created for that client. Never use the primary owner token or the operator
token (`server.token`). Cookies are ignored and MCP has no separate token type
or scope. The REST data API remains public. The live tool list and client setup
instructions are available at `/server/help/mcp`.

## Public discovery and reporting

The server publishes `/.well-known/llms.txt` (also `/llms.txt`),
`/.well-known/security.txt`, and an optional `/.well-known/pgp-key.asc` when a
public key is configured. Security reports can be submitted through the
security page; the emailed one-shot status link opens
`/server/security/report/{tracking_id}`. Swagger and GraphQL explorers are
available from the server help page.

`GET /api/autodiscover` returns server identity and version, supported API
versions, the primary URL, and the endpoint map for `airports-cli` and other
programmatic clients. It is machine discovery; Tor and I2P addresses are
advertised only when the overlay is enabled and the operator opts in to
exposure.

## SMTP — Outbound Email (optional)

Used for operator notifications (e.g., backup failure alerts) and delivery of public contact-form submissions. Auto-detected when SMTP config is present.

```yaml
smtp:
  host: smtp.example.com
  port: 587
  username: user@example.com
  password: "<env or vault>"
  from:     "airports@example.com"
  tls: starttls
```

This project has no user accounts, so transactional email (signup, password reset) does not exist.

## Self-Update — GitHub Releases

When `airports --update` is invoked, the server checks GitHub Releases for its configured channel, downloads the matching `{os}/{arch}` binary, verifies the SHA-256 checksum, and replaces itself in place via atomic rename. Channels are `stable`, `beta`, and `devel`; `daily`, `rolling`, `dev`, and `development` are accepted aliases for `devel` and are stored canonically. The `devel` channel compares release publication time with the running binary's embedded build epoch and ignores `defer_days`.

Disabled inside Docker — the user is instructed to `docker pull` instead.

## Reverse Proxy — Auto-detected

The server auto-detects when it is behind a reverse proxy via `X-Forwarded-Proto`, `X-Forwarded-Host`, and `X-Forwarded-For` headers and adapts:

- `DOMAIN` (no manual `server.yml` entry needed)
- Scheme (`http` vs `https`)
- Remote IP (uses the leftmost public address from `X-Forwarded-For`)

Works out of the box with nginx, Caddy, Traefik, HAProxy, and Cloudflare.

## Container Runtime — Docker / Podman

The image runs unprivileged. Two volumes mount the entire runtime state:

```yaml
volumes:
  - ./volumes/config:/config:z
  - ./volumes/data:/data:z
```

Compatible with Docker, Podman, containerd, and any OCI-compliant runtime.

## What the Server Does NOT Integrate With

- **No OAuth / OIDC / SAML** — no user accounts exist.
- **No external database server required** — embedded SQLite for operational state.
- **External cache is optional** — in-process memory is the default; Redis or Valkey can be configured for shared cache and rate-limit state.
- **No external scheduler** — built-in cron (do not deploy host cron / systemd timers).
- **No mandatory telemetry or phone-home** — optional consent-gated analytics may load in visitors' browsers. The server's outbound HTTPS calls are limited to GeoIP refresh, ACME (if enabled), and self-update (when explicitly invoked).
